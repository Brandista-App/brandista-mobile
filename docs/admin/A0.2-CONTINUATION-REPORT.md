### Backend (`brandista-mvp`)

- `SUPER_ADMIN` and `BRAND_ADMIN`, preserving `CUSTOMER` and legacy `ADMIN` behavior. Public registration still creates only customers.
- One Flyway V10 Java migration extends the existing users role constraint and adds the previously absent `brand_administrators` relation and singleton `admin_access_guard` lock. It uses MySQL/H2-specific syntax only for dropping the existing check constraint. Existing V1–V9 migrations, including the upstream address/inventory/order migration, are unchanged.
- Offline `admin-bootstrap` Spring profile: no HTTP listener, interactive hidden password prompts or explicitly mounted local credential file, normal validation/BCrypt hashing, refuses bootstrap when an active super admin exists, never promotes an existing customer, closes the application after completion.
- Serialized bootstrap/account status operations prevent concurrent removal of the last enabled super admin. No administrator deletion or role-change endpoint was added.
- Live database checks for admin role/status on each bearer request; assignment changes are read from the database. Disabled administrators lose access on their existing tokens.
- Super-admin-only account management using safe response DTOs (no password hashes). Legacy `ADMIN` retains catalogue/application management but cannot provision privileged accounts.
- Existing brand APIs reused for creation/management; assigned brand admins can list/read only assigned brands. Brand/category/application mutations remain platform-only.
- Existing product APIs reused with server-side ownership checks for create, read, update, publish, unpublish and deactivate, including both source and destination brand on reassignment. Product lists are scoped in SQL before pagination. The newly fetched upstream stock endpoint also uses live admin-role and brand-ownership checks; own-brand and cross-brand stock operations have integration coverage.
- New integration coverage exercises first/second super-admin provisioning, last-admin protection, cross-brand denial, scoped lists, publication, assignment revocation and disabled-token denial. Migration-history test now expects V10.
- Local secrets/logs excluded from Git and future Docker build contexts.

## Safe first-super-admin provisioning

From `C:\development\brandista\brandista-mvp`:

1. Configure the ignored `.env` using `.env.example`, unique generated MySQL/JWT secrets, and the explicit local CORS origin. Preserve an existing volume and its credentials; never use `down -v` to repair authentication.
2. Start Docker Desktop, then `docker compose up -d mysql` and `docker compose build backend`.
3. In an interactive terminal run `docker compose run --rm --no-deps backend --spring.profiles.active=admin-bootstrap`.
4. Enter the first owner's email and a unique password twice. Passwords require at least 12 Unicode characters and no more than 72 UTF-8 bytes. Input is hidden and does not appear in command arguments or application logs. Bootstrap has no public HTTP endpoint.
5. The process exits after saving the BCrypt hash. Repeat bootstrap is refused while any active super admin exists. Start normally with `docker compose up -d backend` and sign in at the administrator URL.

For unattended **local** provisioning, the profile accepts `BOOTSTRAP_CREDENTIALS_FILE`, containing JSON `{email,password}`. Restrict the host file to the operator, keep it outside Git and the image, mount it read-only, pass only its path, and remove the temporary bootstrap file after provisioning. Do not enable this profile on the normal HTTP service.

This session generated the local owner's credentials in `C:\development\brandista\brandista-mvp\secrets\admin-access.json`, in an ignored directory whose Windows ACL is restricted to the current user. Demo administrator credentials are recorded there by the API rehearsal. Read this file locally; do not paste it into issues, reports or Git. No password is hardcoded in application code.

## Demo onboarding steps

1. Sign in as super admin. Under **Create brand**, create **Cedar Studio**, **Indigo Loom**, and **Saffron Works**, with unique lowercase slugs such as `cedar-studio`, `indigo-loom`, `saffron-works`. Brands start active. Edit the brand to change metadata/status.
2. Create an active category, such as **Demo Collection**, slug `demo-collection`.
3. Under **Administrator access**, create three `BRAND_ADMIN` accounts, each with a unique real email and strong initial password, selecting exactly its intended brand. Share credentials privately with each administrator. This is controlled account creation; **no invitation email is sent**, and no email/password-reset infrastructure was invented. For another super admin, choose `SUPER_ADMIN`; brand selections are ignored.
4. Sign out; log in as each brand administrator at the same admin login URL. Verify only its assigned brand and products appear. Under **Create product**, enter name, unique slug, description, assigned brand, category, PKR price and availability. Save creates a draft. Use **Edit** to change details, then **publish**.
5. Open the customer storefront in a separate browser session. Browse `/products`, filter by brand, and open the product. Drafts are hidden; published products with active brand/category are discoverable. Use **unpublish** to remove a product from discovery and **deactivate** for permanent catalogue retirement.
6. Test cross-brand ownership using the API rehearsal; hiding frontend controls alone is not evidence of authorization.

To reproduce the real API rehearsal from the storefront repository (Python 3 required):

```powershell
python scripts/admin/verify-a02.py --credentials-file C:/development/brandista/brandista-mvp/secrets/admin-access.json
```

This creates a new suffixed demo set on each execution. Run against a local demonstration database with a sole enabled super admin at the start; it deliberately checks last-admin protection before creating and disabling a second test super admin. It preserves the three enabled demo brand admins and their published products at completion.
