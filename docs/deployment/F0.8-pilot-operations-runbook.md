# F0.8 Controlled Pilot Operations Runbook

## Current authorization and environment

There is currently **no pilot environment** and no approved external tester access. Do not invite customers or partners until the staging verification report recommends a pilot and an owner approves the host, scope, cohort, consent/privacy notice, retention, and incident contacts. F0.8 currently prepares a local rehearsal only; it is not internet staging.

## Roles and access

- Project owner: select/approve hosting, allowed origin, tester cohort, budget and pilot window.
- Deployment operator: manage staging secrets, deploy reviewed code, verify migrations/health and preserve backups.
- Data operator: provision only fictional sample catalogue rows and disposable test users on the isolated staging database.
- Pilot participants: no access until enabled; issue individual disposable accounts, never share a common password in chat or email. Share credentials through an approved password manager and require rotation/removal after the pilot.
- Incident lead: named before any pilot; owns disable/rollback decisions and participant notification.

## Local isolated rehearsal

Prerequisites: Docker Desktop/Compose, Java 21 for local tooling, supported Node.js, both sibling repositories, and a disposable database. This rehearsal uses the existing local Compose stack with a distinct Compose project and database/volume.

From the backend repository:

```powershell
Copy-Item .env.staging.example .env.staging
# Edit .env.staging locally: replace every REPLACE_ value; generate a fresh Base64 JWT key with at least 32 random bytes.
docker compose --project-name brandista-f0-8-local --env-file .env.staging config --quiet
docker compose --project-name brandista-f0-8-local --env-file .env.staging up --build -d
docker compose --project-name brandista-f0-8-local --env-file .env.staging ps
Invoke-RestMethod http://127.0.0.1:8082/actuator/health/liveness
Invoke-RestMethod http://127.0.0.1:8082/actuator/health/readiness
docker compose --project-name brandista-f0-8-local --env-file .env.staging logs --tail 150 backend mysql
```

The database port binds to loopback at 3310 and backend at 8082; use only disposable local data. Verify both health responses report `UP`; inspect redacted backend logs for Flyway applying migrations V1–V7. Compose's MySQL health check confirms a server ping; backend readiness verifies the application DB connection. The separate project name scopes its containers and named volume.

From the frontend repository, create ignored `.env.staging` from `.env.staging.example`, then:

```powershell
npm ci
npm run build -- --mode staging
npm run preview -- --host 127.0.0.1 --port 4173 --strictPort
```

Open `http://127.0.0.1:4173`. This builds static production assets, but Vite Preview is only a local check server. The API URL embedded in the assets must match the backend port. CORS must match the exact browser origin. For remote staging, replace the localhost API root with the provisioned HTTPS API URL and set CORS to the exact HTTPS frontend origin; never publish local example values.

Start migrations only against an empty, dedicated pilot database or a backed-up non-production staging database. Do not copy production customer records. No seed script is present; no approved/demo records are loaded automatically. Catalogue preparation requires a designated operator and supported admin API after the disposable DB and account roles have been verified. No SQL role elevation procedure is authorized by this runbook.

Stop without deleting persistent local rehearsal data:

```powershell
docker compose --project-name brandista-f0-8-local --env-file .env.staging down
```

Reset only after confirming the project name and all data in that project is disposable:

```powershell
docker compose --project-name brandista-f0-8-local --env-file .env.staging down -v
```

The reset command permanently deletes that project's DB volume. It has not been run. Never use it with another project name or a remote/shared environment.

## Service health and logs

For local rehearsal, use liveness and readiness endpoints above and `docker compose ... ps`. Review `docker compose ... logs --tail 150 backend mysql` locally; do not paste raw logs into tickets because request or environment material may be present. The production log destination, access roles, retention and alert channel are not configured. Before remote pilot, the owner must name the provider's log console, authorized operators, retention period and on-call contact.

## Data protection, backup, and restore

No remote staging database or backup service exists. Before a pilot, require automated encrypted backups, retention, restricted backup access, documented recovery-point/recovery-time targets, and a restore drill into an isolated database. Never test restore against the source DB. Assign a named backup and restore owner. Do not represent an untested snapshot as recoverable.

## Supported and unsupported participant actions

If live staging is eventually enabled, currently implemented journeys are public brand/category/product discovery, product details, customer registration/login, customer-owned saved-address API, and persistent customer cart add/update/remove. Cart totals are display calculations only. The frontend keeps bearer tokens in memory; reloading requires signing in again.

Checkout and payment are absent: no charge can or should be attempted, and no successful order/receipt exists. Order history, inventory reservation/counts, fulfilment, delivery tracking, cancellation and refunds are also absent. Product availability is not stock. Pilot invitations must describe the experience as catalogue/account/cart testing only and must not promise transactions or delivery.

## Incident response and rollback

Before enabling a remote pilot, name the incident lead, backup owner and hosting operator. Record deployment version, migration state and restore point. For a critical defect, the incident lead pauses access by disabling public ingress to both frontend and API at the hosting edge, preserves redacted logs, and contacts the owner. There is no application-level pilot kill switch or allowlist today. The deployment operator returns the previous compatible application artifact only after checking migration compatibility; do not roll back schema migrations or restore over current data without the owner's explicit recovery decision. No automated rollback is configured. With only the local rehearsal, stop the local frontend and Compose project; preserve data unless the explicit reset command above is approved for disposable data.

## Pre-pilot checklist (all items required)

- [ ] SRS / pilot scope and permitted personal data reviewed and approved.
- [ ] Host, domain, HTTPS ingress, exact CORS/API URLs, secret store and cost limit approved.
- [ ] Dedicated staging DB provisioned; migration applied and persistence/restart verified.
- [ ] Backup/restore drill passed; restore owner and incident lead named.
- [ ] Fictional catalogue data reviewed; no production customer data copied.
- [ ] Disposable individual participant accounts provisioned and securely shared.
- [ ] Health, logs, access controls, alert route and pilot disable steps verified.
- [ ] Browsing/auth/cart journeys, validation, ownership denial, direct route refresh, mobile/desktop and database/API failure behavior tested on the actual deployed URL.
- [ ] Participants told that checkout, orders, payments and delivery are unavailable.
- [ ] Project owner explicitly approves pilot cohort, dates, notice and data retention.

## Post-test checklist

- [ ] Disable pilot access on the approved end date or incident request.
- [ ] Revoke/delete temporary accounts according to the approved retention plan.
- [ ] Review redacted error/security logs and participant feedback.
- [ ] Record defects, migration/backup state and actual pilot scope.
- [ ] Confirm whether staging data is retained or reset; get owner approval before destructive deletion.
