# F0.8 Deployment Assessment

Date: 2026-10-14. Assessment baseline: merged F0.7 main branches in `brandista-mobile` and `brandista-mvp`.

## Initial recommendation

Proceed only with deployment preparation and a local, isolated container rehearsal using the existing Spring Boot, MySQL, Vite and Docker Compose stack. Do not create a public deployment or choose a cloud platform in code: the SRS, hosting account, domain, TLS termination, staging DB, secret store and budget are not available. A local Compose stack is not remote staging and cannot qualify as a pilot environment.

The simplest eventual topology supported by the code is a static production build of the React/Vite client served over HTTPS, a Spring Boot API, and a dedicated MySQL 8.4 database. An HTTPS ingress must set the exact frontend CORS origin and route `/api/v1` to the backend. The repository has an API Dockerfile and local backend/MySQL Compose file; it has no frontend container or selected hosting/deployment manifest. Provider-specific infrastructure is therefore out of scope until the owner chooses a provider.

## Hosting, external services, and costs requiring owner input

No hosting account, domain, public URL, ingress/TLS provider, managed database, secret manager, backup service, monitoring, email provider, payment processor or budget is defined. Their prices cannot be derived from repository contents. The owner must select and authorize a provider, region, service sizes, retention/backup policy and monthly cost ceiling before a cost estimate or remote deployment can be prepared.

No external payment integration should be added without separate authorization and provider credentials. No payment is implemented or simulated. The current frontend disables checkout; pilot participants can browse, register/sign in and use the cart only if the real backend and database are available. No order or payment confirmation exists.

## Proposed F0.8 work boundary

1. Keep the assessment and deployment instructions in the frontend documentation repository.
2. If useful for repeatability, add only a local containerized staging rehearsal with a separately named Compose project/database/volume, safe placeholder-based environment template, and a production frontend build. Label it local and unverified while Docker is unavailable.
3. Do not add provider-specific infrastructure, public port exposure, TLS shortcuts, production credentials, fake checkout, or destructive reset automation.
4. Test manifests/configuration and all checks that do not require Docker. Mark MySQL migration, remote deployment, backup/restore and pilot journeys blocked/not run until their dependencies are actually supplied.
