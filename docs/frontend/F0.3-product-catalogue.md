## Audit findings

- Read `F0.1-implementation-report.md`, `F0.2-implementation-report.md`, and `docs/qa/QA-01-frontend-verification.md`. The F0.1 foundation already supplied public product cards, keyword/category/sort controls, page navigation, a product detail route, loading/empty/error handling, and CSS product art. F0.2 fixed pagination and added product retry handling.
- No approved Brandista SRS or standalone F0.3 acceptance note was found in either repository. The backend `B0.14-api-contract.md`, public product controller/response DTO and product discovery tests are the available contract sources.
- The backend controller supports `page` (zero-based), `size` 1–100, `keyword` (up to 100 characters), positive `brandId` and `categoryId`, and only `default`, `price_asc`, and `price_desc` sorting. Public product reads need no token. Product detail is looked up by slug and returns 404 when unavailable.
- Product response has no image URL, variant/size list, stock count, discount or review fields. The existing CSS illustration remains decorative; the UI does not claim product photography or invent those facts. `description` is nullable/optional and has a neutral fallback.
- Existing cart API supports `POST /api/v1/customers/me/cart/items` with a positive `productId` and `quantity`, requires a CUSTOMER bearer token, and returns the updated cart. The product page can therefore submit a selected quantity.

## Implemented

- Added a server-side brand filter alongside the existing category and keyword filters. Both filter lists request page 0 with size 100, the backend's documented maximum, and display a retryable filter error if metadata cannot load.
- Preserved filter/search values in URL parameters, synchronized the shared search field to the active `keyword`, and constrained it to the backend's 100-character limit. Changing filters resets pagination; changing page preserves filters.
- Added request sequencing to the catalogue so a slower response for an earlier filter/page cannot replace newer results.
- Kept only documented sorting choices and server-side search/filtering. Existing no-results state and clear-filters action remain functional.
- Added a quantity control to product details, constrained to the positive 32-bit quantity range supported by the cart API. Add-to-bag submits the selected quantity only for an authenticated customer and available product; unavailable products remain disabled. Duplicate submissions are disabled while a request is in flight.
- Kept product detail fields aligned with the DTO, mapped product 404 to an unavailable message, and retained retry handling for detail load errors.
- No application mock product data was added. Test fixtures are defined only in `src/app.test.tsx` and never returned as live catalogue content.

## API integration contract used

Configured root: `VITE_API_BASE_URL`, default `http://localhost:8080/api/v1` (`.env.example`). No new endpoint was introduced.

| UI behavior             | Actual request                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Product listing         | `GET /products?page={page}&size=12&sort={default\|price_asc\|price_desc}[&keyword={text}][&brandId={positiveId}][&categoryId={positiveId}]` |
| Brand filter options    | `GET /brands?page=0&size=100`                                                                                                               |
| Category filter options | `GET /categories?page=0&size=100`                                                                                                           |
| Product detail          | `GET /products/{slug}`                                                                                                                      |
| Add selected quantity   | `POST /customers/me/cart/items` with `Authorization: Bearer {accessToken}` and JSON `{ "productId": 42, "quantity": 3 }`                    |

The paged product response is `{ "content": [...], "page": 0, "size": 12, "totalElements": 1, "totalPages": 1 }`. Each public product contains `id`, `name`, `slug`, nullable `description`, `brandId`, `brandName`, `categoryId`, `categoryName`, `price`, `currency: "PKR"`, and `availability: "AVAILABLE" | "UNAVAILABLE"`. No image or stock-count field exists in this schema.

The centralized client sends JSON content type for bodies, attaches bearer auth when set, converts network failures to a user-facing message, and maps the backend error `message` and `fieldErrors`. Backend validation/conflict/auth statuses remain server-owned (commonly 400/404/409/401/403). Product/category/brand discovery is public; cart mutation is CUSTOMER-protected. Configure backend `CORS_ALLOWED_ORIGINS` with the exact frontend origin, such as `http://127.0.0.1:5173`; wildcard is not supported by the backend configuration.
