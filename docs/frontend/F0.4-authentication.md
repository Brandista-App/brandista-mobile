## Audit findings and contract source

- Reviewed the F0.1, F0.2, F0.3 implementation reports and `docs/qa/QA-01-frontend-verification.md`, frontend routes and API client, and the backend's `B0.14-api-contract.md` plus the registration/login request and response records, security configuration, password policy and authorization tests.
- No approved Brandista SRS or separate F0.4 acceptance criteria were available in either repository; the prior reports record this gap. Requirements coverage against the product SRS therefore remains unverified.
- The verified backend contract defines `POST /api/v1/registrations` with `{email,password}` and a `201` response `{id,email,createdAt}`; registration normalizes email and enforces at least 12 Unicode code points and no more than 72 UTF-8 password bytes. Duplicate email returns `409`; validation failures return `400` with `fieldErrors`.
- Login is `POST /api/v1/auth/login`, also with `{email,password}`. Success returns `{accessToken,tokenType:"Bearer",expiresIn,account:{id,email,role}}`; invalid credentials return `401`. Access tokens are signed bearer tokens with a default 900-second lifetime (configurable to at most 3600 seconds). The backend has no refresh or revocation endpoint and uses stateless JWT authentication.
- Customer-only API routes require `CUSTOMER`; customer record ownership is based on the JWT subject. The frontend protects customer pages for usability; backend authorization remains authoritative.
- `GET /api/v1/customers/me/addresses` is the available customer information endpoint. There is no customer profile/me endpoint in the documented contract. The account heading uses only the authenticated login response's email; addresses come from the actual addresses API.

## Implemented

- Added a shared protected-route guard for `/cart`, `/account`, and `/account/addresses`. Guests are redirected to `/sign-in` with their internal pathname and query preserved. Sign-in returns to that destination; untrusted external paths are rejected.
- Kept public browsing routes available to guests. The product detail's add-to-bag action retains its sign-in prompt.
- Registration and login continue to call the verified backend API functions. Registration validates the email, 12-code-point minimum and 72-byte maximum locally; field errors are associated with form controls. Successful registration returns to sign-in with a confirmation and the returned email prefilled. Duplicate, validation, unavailable-server and invalid-credential cases receive non-secret feedback.
- Added an accessible password visibility toggle and pending-submit protection. A successful login accepts only a `CUSTOMER` account response for the customer storefront.
- Access tokens remain in JavaScript memory only. No password or token is written to local/session storage or cookies. Sign-out clears the token and account state. When a protected request returns `401`, the API client clears the bearer token, notifies auth state, and protected routes return to sign-in. The next protected request detects token expiry; there is no proactive expiry timer, refresh, or server-side sign-out because the backend provides no such endpoint. A page reload clears the session.
- Added tests for registration request/validation/duplicate handling, successful login and intended-route return, guest protection, sign-out, unauthorized-session cleanup, rejected credentials, visibility toggle, and repeated-submit prevention. Existing product/catalogue regression cases remain in the suite.

## Local configuration and reproduction

- Frontend API base: `VITE_API_BASE_URL`, default `http://localhost:8080/api/v1` (see `.env.example`). This setting contains no secret.
- Run the frontend using `npm install` and `npm run dev -- --host 127.0.0.1` from the frontend root. The configured backend must be reachable at the API base URL.
- Before browser integration, set backend `CORS_ALLOWED_ORIGINS` to the exact frontend origin (for example `http://127.0.0.1:5173` or `http://localhost:5173`; these are distinct origins). The backend B0.14 contract allows only explicitly listed origins and no wildcard.
- Current backend probes: `Get-NetTCPConnection -LocalPort 8080 -State Listen -ErrorAction SilentlyContinue` found no listener; the health request timed out after four seconds; `docker compose ps --format json` failed because the Docker Engine named pipe was unavailable. These checks prove the current local backend runtime is unavailable, not whether application code or database credentials are the underlying cause today.
- Run verification with `npm test -- --reporter=dot --pool=forks --maxWorkers=1`, `npm run lint`, `npm run build`, and `npm run format:check`.
